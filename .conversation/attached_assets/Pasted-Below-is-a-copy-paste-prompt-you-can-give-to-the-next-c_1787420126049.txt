# Move My Car — Full Application Logic and Next Development Prompt

You are working on a full-stack QR-code vehicle contact application called **Move My Car**.

The application allows vehicle owners to create printable QR-code stickers. When somebody scans a QR code, they can contact the vehicle owner through Call or Text buttons without seeing the owner's real phone number.

The dashboard must support multiple users. Each user must see only their own QR codes, settings, statistics, and scan logs.

Do not store plain-text passwords. Store only bcrypt password hashes in PostgreSQL.

# Main application nodes

## 1. User node

Each dashboard account is a user.

Database table:

```text
users
├── id
├── username
├── password_hash
└── created_at
```

Rules:

- `username` must be unique.
- Passwords must be hashed with bcrypt.
- Never store plain-text passwords.
- Never store passwords in Google Sheets.
- User ID must be stored in the login session.
- User ID must be used to filter all private data.

Example user:

```text
username: owner
password: bcrypt hash
```

The first user can be created from the existing `DASHBOARD_PASSWORD` environment secret using the default username:

```text
owner
```

---

## 2. Session node

Use PostgreSQL-backed Express sessions.

Session values:

```ts
{
  isAuthenticated: boolean;
  userId: number;
  username: string;
}
```

Session behavior:

- Use `express-session`.
- Use `connect-pg-simple`.
- Store sessions in PostgreSQL.
- Use an HttpOnly cookie.
- Use `SameSite=Lax`.
- Use `Secure` cookies in production.
- Require `SESSION_SECRET`.
- Do not use a known fallback session secret in production.
- Regenerate the session after successful login to prevent session fixation.
- Destroy the session during logout.

Required session table:

```sql
CREATE TABLE IF NOT EXISTS sessions (
  sid varchar NOT NULL PRIMARY KEY,
  sess json NOT NULL,
  expire timestamp(6) NOT NULL
);

CREATE INDEX IF NOT EXISTS IDX_session_expire
ON sessions(expire);
```

## 3. QR code node

Each QR code belongs to exactly one user.

Database table:

```text
qr_codes
├── id
├── user_id
├── label
├── location
├── forward_phone
├── created_at
└── active
```

Rules:

- `user_id` identifies the owner.
- Dashboard users can only see and modify their own QR codes.
- A user cannot modify another user's QR code.
- A QR code may be active or inactive.
- Inactive QR codes should show an unavailable message on the public scan page.
- `forward_phone` is optional.
- If Twilio is unavailable, the scan page may use the direct phone fallback.
- The direct phone fallback must show a privacy warning.

QR code dashboard functions:

```text
listQrCodes()
getQrCode(id)
createQrCode(data)
updateQrCode(id, data)
deleteQrCode(id)
toggleQrCode(id, active)
updateQrForwardPhone(id, phone)
generateQrImage(id)
printQrCode(id)
```

Every private QR query must include:

```ts
where(
  and(
    eq(qrCodesTable.id, qrId),
    eq(qrCodesTable.userId, req.session.userId)
  )
)
```

## 4. Scan log node

Every scan and contact action should be logged.

Database table:

```text
scan_logs
├── id
├── qr_code_id
├── scanned_at
├── action
└── ip_address
```

Allowed actions:

```text
scan
call
text
```

Rules:

- Public visitors can create scan and action logs.
- Dashboard users can view only logs connected to their own QR codes.
- A public visitor must not see dashboard information.
- A contact action must be tied to a valid QR code.
- If a `scanLogId` is supplied, verify that it belongs to the correct QR code before updating it.

Functions:

```text
logScan(qrCodeId)
logScanAction(qrCodeId, action, scanLogId?)
listScanLogs(userId, limit, qrCodeId?)
```

When a QR code is scanned:

1. Validate the QR code ID.
2. Load the QR code.
3. Insert a scan log with action `scan`.
4. Send a fire-and-forget Google Sheets log.
5. Return public contact information.

Example response:

```json
{
  "qrCodeId": "front-windshield",
  "label": "Front Windshield",
  "location": "Primary Car",
  "active": true,
  "twilioPhone": "+15550000000",
  "directPhone": null,
  "scanLogId": 22
}
```

Example:


Database table:

```text

```

Functions:


Important:

- Never allow user 1 to read user 2's settings.
- Public visitors must not receive the owner phone number directly when Twilio is configured.

# Authentication API functions

## `POST /api/auth/login`

Request:

```json
{
  "username": "owner",
  "password": "user password"
}
```

Logic:

1. Validate username and password.
2. Find the user by username.
3. Compare password with bcrypt.
4. Return 401 if invalid.
5. Regenerate the session.
6. Set:
   - `isAuthenticated = true`
   - `userId`
   - `username`
7. Save the session.
8. Return success.

Response:

```json
{
  "ok": true,
  "username": "owner"
}
```

---

## `GET /api/auth/me`

Unauthenticated response:

```json
{
  "authenticated": false
}
```

Authenticated response:

```json
{
  "authenticated": true,
  "userId": 1,
  "username": "owner"
}
```

---

## `POST /api/auth/logout`

Logic:

1. Destroy the current session.
2. Clear the session cookie.
3. Return success.

Response:

```json
{
  "ok": true
}
```

# User management functions

The authenticated user should be able to create additional dashboard accounts.

## `GET /api/users`

Return:

```json
[
  {
    "id": 1,
    "username": "owner",
    "createdAt": "2026-08-22T00:00:00.000Z"
  }
]
```

Never return `password_hash`.

## `POST /api/users`

Request:

```json
{
  "username": "driver2",
  "password": "secure-password"
}
```

Validation:

- Username minimum 3 characters.
- Password minimum 6 characters.
- Username must be unique.
- Password must be bcrypt hashed.

## `DELETE /api/users/:id`

Rules:

- Do not allow a user to delete their own account.
- Delete or safely transfer that user's QR codes.
- Delete or safely preserve that user's scan logs.
- Delete that user's settings.
- Return a clear error if the user does not exist.

Recommended future improvement:

Add an admin role so only administrators can create and delete accounts.

# Twilio logic

Voice webhook:

```text
POST /api/twilio/voice
```

SMS webhook:

```text
POST /api/twilio/sms
```

Rules:

- Validate `X-Twilio-Signature` when Twilio is configured.
- Do not require dashboard login.
- Do not expose the owner's real number to public users.
- Forward calls to the correct owner's number.
- Forward SMS messages to the correct owner's number.

Important future improvement:

The current Twilio webhook must be updated so the proxy number or QR code identifies the correct user. A single global `OWNER_PHONE` is not sufficient for multiple users.

Recommended routing options:

```text
Option A:
Each user gets a separate Twilio phone number.

Option B:
Store a Twilio number per user and map incoming `To` number to user.

Option C:
Create a short-lived contact token tied to the QR code and pass it to the Twilio route.

Option D:
Use a QR-specific forwarding configuration and separate Twilio webhook paths.
```

The best production approach is:

```text
twilio_numbers
├── id
├── user_id
├── phone_number
└── active
```

Then resolve the owner using the incoming Twilio `To` number.
